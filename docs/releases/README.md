# Стиль описаний релизов

Пишем для пользователей CAS: спокойно, уверенно и с акцентом на пользу в работе с музыкой. Текст должен помогать понять, зачем обновляться, без рекламных преувеличений.

- Начинаем с короткого описания главного изменения и его пользы.
- Группируем небольшие визуальные правки в «Обновлённый внешний вид». Размеры логотипов, отступы и отдельные настройки оформления не перечисляем.
- Описываем результат: «меньше нагрузки на компьютер», «удобнее управлять воспроизведением». Детали реализации, внутренние процессы и историю работы оставляем в технической документации.
- Выделяем несколько существенных изменений. Точные детали нужны, если меняется привычный сценарий, совместимость или требуется действие пользователя.
- Не обещаем производительность и надёжность, которые не подтверждены проверкой. Важные ограничения сообщаем простым языком.
- Завершаем вариантами загрузки и необходимой информацией об обновлении.

Описания хранятся в `vX.Y.Z.md`; GitHub Actions использует их при создании релиза. Подробные результаты проверок храним отдельно в `docs/QUALITY_*.md`.
